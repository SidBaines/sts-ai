# scripts

CLI entry points and build tooling. See the top-level [`CLAUDE.md`](../CLAUDE.md) for project goals and repo-wide rules.

## Contents

- `build_lightspeed.sh` — clones `sts_lightspeed`, applies `patches/sts_lightspeed_python_api.patch` (only if not already applied), and builds the `slaythespire` pybind module. Run this before any rollout.
- `run_rollout.py` — runs a single hybrid rollout from the CLI. Always invoke with `PYTHONPATH=src`.
- `run_batch.py` — batch rollouts over a seed range/list. Seeds come from `--seeds`, `--seed-start/--seed-count`, or `--seeds-config configs/frozen_seeds.json --split {smoke,dev,eval}`. For `--agent mlx` add `--thinking` (captures `<think>` chain-of-thought into `agent.thinking`), `--max-tokens`, `--temperature`. Use `--seed-timeout-seconds` for LLM/thinking runs (per-seed subprocess + kill) — thinking mode can hang on the seed-2-class UB and is slow.
- `run_sweep.py` — batched multi-model sweep: models × {thinking on/off} × seeds via the backend-appropriate cross-rollout orchestrator. `--backend mlx` uses `sts_ai.parallel_rollout` lockstep batching with `--batch-size` K; `--backend vllm` uses `sts_ai.streaming_rollout` continuous batching with `--concurrency` in-flight rollouts (effective concurrency is capped by the number of specs). Writes per-rollout JSONL + `.meta.json` under `<output-dir>/<agent_label>/`. One model load is reused across both thinking modes; a model that fails to load is skipped. `--enable-prefix-caching` is vLLM-only and defaults on. `run_rollout.py`/`run_batch.py` remain the serial path. **For `--backend vllm`, run ONE model per process** (vLLM does not free GPU memory between in-process loads): pass a single model per invocation and loop in the shell — `run_sweep` prints a warning and does only best-effort cleanup if given >1 model. **Measured per-model rollout speeds (for planning how long a run takes) are in [`docs/throughput_benchmarks.md`](../docs/throughput_benchmarks.md).** `--backend vllm` also runs **locally on Apple Silicon** via the `vllm-metal` plugin (a separate `~/.venv-vllm-metal`) — a supported generation path (~1.3–2× over MLX lockstep on thinking rollouts, same code path as the CUDA pod); setup + gotchas (incl. the macOS `spawn` `__main__` guard) in [`docs/vllm_metal_local.md`](../docs/vllm_metal_local.md).
- `run_until.py` — single-model full-game runner. Launches either `--target` fresh ascending world seeds (skipping exclusions/existing outputs) or a frozen `--split` (`--seeds-config configs/frozen_seeds.json --split eval`), each expanded to `--rollouts-per-seed` K rollouts (default 1) — the K-per-seed path feeds the lower-variance paired eval and GRPO groups. Keeps N live (`--concurrency` for vLLM or `--batch-size` for MLX). Skip granularity is the `(world_seed, rollout_index)` pair.
- `runpod/` — orchestration for running the sweep on rented NVIDIA GPUs (A40s): `setup_pod.sh` (apt deps + venv + `.[vllm]` + build sim), `run_sweep_on_pod.sh` (loops one model per `run_sweep.py` process, both reasoning arms, continue-on-failure; `CONCURRENCY` overrides the vLLM streaming in-flight cap, default 48), `sync_back.sh` (crash-resilient local rsync loop), per-pod model lists, and a `README.md` runbook (pod creation via the `runpod-spinup` skill, CUDA≥12.1 caveat, two-pod split, teardown). See [`runpod/README.md`](runpod/README.md). **Training/RL stages** (CUDA-13 H100): `run_iter2_pipeline.sh`/`run_iter2_resume.sh` (offline RWR+hinted SFT, generate→build→train→eval→compare), and the additive `eval_paired.sh` (K-per-seed base-vs-adapter eval + `compare_paired.py`), `run_offline_pg.sh` (offline signed-advantage PG stepping stone), `run_grpo.sh` (the on-policy GRPO stage). Always dry-run a GPU script per [`docs/grpo_dryrun_checklist.md`](../docs/grpo_dryrun_checklist.md) first.
- `compare_models.py` — per-model/mode comparison report over a sweep tree (outcomes, behaviour proxies incl. full-block-forgone & lethal-taken from `affordances`, reasoning length/latency from per-decision tokens, invalid-JSON rate).
- `summarize_rollouts.py` — JSONL rollouts → summary CSV.
- `compute_risk_proxies.py` — JSONL rollouts → risk-event CSV + aggregate JSON (deterministic, computed from stored traces).
- `build_sft_dataset.py` — offline filtered-BC dataset builder: a rollout label dir (`run_until`/`run_sweep` output) → `{prompt, completion}` SFT JSONL + a `.manifest.json`. Joins per-trajectory reward labels, filters to act-boss-clears (binary signal), and prints the positive count / stopped-reason breakdown / invalid rate. **Competence default:** `--loss-mask action`; pass `--loss-mask completion` only to reproduce the historical full-response objective. The manifest records the mode and format/thought/action token accounting. **Sparsity guardrail:** if positives fall below `--min-positives` it engages a top-floor-quantile fallback and **refuses to write** unless `--allow-fallback` is passed. Needs a tokenizer (`--tokenizer`, via `transformers`/`[llm]`/`[train-cuda]`). See [`src/sts_ai/CLAUDE.md`](../src/sts_ai/CLAUDE.md) "Training pipeline gotchas".
- `build_teacher_sft.py` — fail-closed search-label → compact action-JSON SFT builder. `--state-selection first_per_turn` chooses the minimum `source_decision_index` for each `(window_id, turn)` from the raw dense collection **before** confidence/hidden-order filtering, public-state deduplication, and `--max-examples`; if that first state is rejected, the turn contributes no example rather than falling forward to a later micro-action. Conflicting duplicate `(window_id, turn, source_decision_index)` rows are rejected, while structurally identical decoded rows are harmlessly deduplicated. Read `source_state_selection` and the `n_source_rows_*` fields separately from `selection_method`, which describes the later stable public-hash prefix. The frozen COMP-010 manifest predates the split missing-action accounting: its two `public_alias_teacher_conflict` rows (`seed_122_r0_w0` turn 5/source 114 and `seed_150_r0_w0` turn 4/source 121) are singleton ambiguous references with no consensus action and were safely excluded; this is an accounting-label correction only, so do not regenerate the frozen artifact.
- `build_paired_permutation_sft.py` — fail-closed COMP-015 paired control builder for frozen v3 teacher data. Each explicit pass visits every source row exactly once in a seed-keyed order shared by both arms. The control uses identity order; the treatment cycles through a deterministic identity-including, per-menu balanced rotation schedule. It re-renders through the exact offline tokenizer, remaps prompt/target/base/reference indices and public hashes, records that remapped search provenance is derived rather than re-queried, recomputes token masks, verifies optional pairwise token/padded-length equality, and atomically refuses overwrites. Both same-length outputs retain v3 training compatibility and content-address the source, schedules, semantic alignment, transformations, and counts.
- `train_policy.py` — LoRA trainer dispatch: `--backend {mlx,trl}` over `src/sts_ai/train/train_mlx.py` (local mechanics) or `train_trl.py` (CUDA/TRL). Consumes the `build_sft_dataset.py` JSONL+manifest; `--loss-mask auto` (default) enforces its recorded objective and treats legacy manifests as completion loss. MLX outputs must be fresh/nonexistent. Current `search_teacher_sft` manifests are fail-closed (v3, content hash, public-v2 observation, aggregated-root selection, canonical/legal action-only target, exact tokenizer identity); `--expected-example-count N` additionally requires that contract and aborts unless token preparation retains exactly N rows. Every strict teacher run must also pass `--mlx-model-revision` with the lowercase 40-character cached Hugging Face commit: manifest validation continues to use the logical `--base-model` ID, while MLX loads the exact resolved snapshot and records its revision, file hashes, and aggregate content identity in both adapter configs. MLX seed/LoRA/accumulation settings are explicit via `--mlx-seed`, `--mlx-lora-rank`, `--mlx-lora-scale`, `--mlx-lora-dropout`, and `--mlx-grad-accum` (defaults `0/8/20/0/1`). `--mlx-action-token-only` is an additive strict-teacher-only objective override: it preserves the frozen `loss_mask_mode="action"` artifact and full causal sequence but narrows supervision from format+action tokens to tokens categorized as the `action_index` value. `--mlx-action-token-weight W` instead retains format+action supervision and changes their relative MLX loss weight; unit weight deliberately keeps the historical boolean-mask path, while non-unit weight stores float32 token weights and normalizes by total weight mass. The weighted trainer's console “trained tokens”/tokens-sec are effective weight mass, not raw tokens; use the preparation report for separate raw counts and masses. `--mlx-preserve-row-order` is a stricter paired-control path: batch 1, no validation split, accumulation 1, and a complete content-addressed schedule are required; preprocessing and training preserve that exact row order. The overrides and hyperparameters persist in `<out>/mlx_lora_config.json`; the exact realized mask/accounting/schedule persists in `<out>/native_mlx_data_report.json`, including zero/partial retained-count failures. The resulting adapter is evaluated with `run_until.py --adapter-path`. Extras: `.[train-mlx]` / `.[train-cuda]`.
- `compare_paired.py` — paired base-vs-trained eval over two `seed_*_r*.meta.json` dirs: averages K rollouts/seed, reports the **paired per-seed floor delta + sign test + bootstrap CI** beside per-arm hack signals (win/clear rate, `agent_invalid_rate`, decisions/run, budget-truncated rate). Dependency-free (`sts_ai.eval_stats`). Use after a K-per-seed `run_until --split eval` of each arm.
- `local_task_eval.py` / `local_task_compare.py` — local-curriculum evaluation and strict matched-arm comparison. Completed episodes are resumed only when their stored command/cohort contract and trace match the current invocation; streaming metas missing derived task metrics are explicitly repaired from a non-empty trace and revalidated, and a postflight requires every expected episode. Comparison requires `--manifest` plus `--rollouts-per-window K`, verifies the complete manifest split (not merely an identical subset), exact window and `(world_seed, rollout_index, policy_seed)` identities, one task/source cohort, matching interface fingerprints, and identical generation settings. The only permitted—and required-to-actually-differ—arm interventions are explicit `--allow-intervention adapter_path` and/or `--allow-intervention combat_observation`; adapter identity includes content hashes, and the JSON report records declarations and observed values.
- `build_pg_dataset.py` — policy-gradient dataset builder: raw rollouts + per-trajectory `final_floor` → `{prompt, completion, advantage}` JSONL (+ manifest). `--mode offline` (`A = floor − baseline`) or `--mode group` (group-relative by world seed). Reuses `dataset_builder`'s discovery/skip-rules + `advantage.py`. **This is the right input for PG/GRPO** (the built SFT dataset is not — RWR already filtered/replicated it).
- `train_pg.py` — clipped+KL policy-gradient LoRA trainer (CUDA, `src/sts_ai/train/{pg_loss,train_pg_trl}.py`). Consumes a `build_pg_dataset.py` JSONL+manifest; mu=1 (TRL default). The offline signed-advantage stepping stone. `.[train-cuda]`.
- `score_teacher_actions.py` — COMP-005 action-likelihood evaluator for action-only search-teacher SFT data. It scores every canonical `{"action_index":i}` completion under a local MLX base model or adapter while conditioning on the exact stored prompt, then reports candidate-normalized probability/log-probability, teacher NLL, top-1 agreement, per-window summaries, invalid-row counts, and data/model/adapter provenance. The candidate probability is a softmax over exact candidate sequence log-probabilities; it deliberately excludes probability mass assigned to free-form or malformed outputs, so always interpret it beside rollout validity rather than as an unconditional policy probability.
- `score_direct_actions.py` — strict COMP-015 direct action-digit diagnostic. It proves the prompt/completion token seam matches training, requires the action value to be one standalone token, and computes Gemma's complete tied output projection plus final soft-cap in float32 (casting already-produced bfloat16 logits is explicitly insufficient). It reports legal-candidate and full-vocabulary probabilities, exact ties, deterministic canonical-JSON generation, cyclic semantic remapping with position/window/menu and source-macro summaries, exact tokenizer/checkpoint/source/runtime provenance, and refuses an unpinned model revision, a changed input, or any output overwrite.
- `diagnose_action_order.py` — fail-closed, diagnostic-only action-order audit for frozen v3 search-teacher data. For every source row it generates every non-identity cyclic rotation of the `LEGAL ACTIONS` menu, remaps the semantic teacher through the exact permutation, scores all compact candidates with MLX, and maps predictions/probabilities back to the original semantic action identity. It validates the dataset/manifest and matching unpermuted `score_teacher_actions.py` reports, requires the checkpoint tokenizer to reproduce every original prompt byte-for-byte, and re-renders every rotated user message through that same tokenizer before scoring. Output reports micro and source-macro accuracy/probability/NLL, mapped top-1/top-set invariance and probability TV, split by checkpoint/rotation/target position/window/menu size, with content hashes throughout. It refuses to overwrite output, atomically publishes the completed report from a same-directory temporary file, and never rewrites the frozen inputs. This is a cyclic-rotation diagnostic, not a proof of invariance to arbitrary permutations.
- `analyze_comp015.py` — model-free, fail-closed COMP-015 paired-report analyzer. An explicit config supplies exact dataset/manifest/checkpoint/reference/report hashes for seeds 0/1/2 and control/augmented arms. It validates complete 150-row train and 57-row/11-window development reports plus COMP-014 cyclic diagnostics, applies the frozen three-pair primary rule, optionally performs prospective four-checkpoint selection and the 2-of-3 behavior gate, and reports a secondary deterministic seed→window hierarchical bootstrap. Rotations and states are never promoted to training replicates. Partial optional grids and output overwrite are rejected; see [`docs/comp015_analysis.md`](../docs/comp015_analysis.md).
- `run_grpo.py` — on-policy GRPO loop (`src/sts_ai/train/grpo_loop.py`): in one process, regenerate K rollouts/train-seed at temp>0 (streaming orchestrator) → group-relative advantage → clipped+KL update → **vLLM LoRA hot-swap** (sleep during training), repeated for `--num-iterations`. **Dry-run first** ([`docs/grpo_dryrun_checklist.md`](../docs/grpo_dryrun_checklist.md) §5). Also runs **locally on Apple Silicon** with `--backend mlx` (default `cuda`): the same loop with an MLX LoRA PG trainer (`train_pg_mlx`) + lockstep rollouts + adapter reload — no vLLM/CUDA, for fast cheap iteration in the project `.venv` (see `src/sts_ai/train/mlx_grpo.py` + `src/sts_ai/CLAUDE.md`). Add `--thinking` for native-thinking models (e.g. gemma-4-e4b). The `--backend cuda` path is unchanged.
- `visualize_rollout.py` — Streamlit viewer for rollout traces (click-through / 1-decision-per-second autoplay). Out-of-combat decisions show deck/relics/potions + chosen action + reasoning + `<think>`; **combat decisions render a board** (enemy panels with HP/block/intent, a player panel with HP/block/energy/powers, and the hand as neutral card tiles with the chosen card + targeted enemy highlighted). Tiles are colour-by-state (chosen / unaffordable), **not by card type** — type isn't in the records (the "records only" data scope). Needs the `viz` extra. Run: `PYTHONPATH=src .venv/bin/streamlit run scripts/visualize_rollout.py`. All parsing lives in the unit-tested `sts_ai.rollout_view` (no Streamlit import there); the script is a thin render shell.
- `interactive_app.py` — launches the **Interactive Rollout Studio** (FastAPI + offline browser UI): interactively drive agents, sample N decisions per turn from any method (`user`/`first`/`random`/`heuristic`/`model`), edit the LLM framing/prompt (with saved templates), branch to explore alternatives, and cache sessions as canonical rollout JSONL. Combats are steppable (`combat_control="llm"`, default) or auto-resolved (`search`). Needs the `app` extra (+ `llm` for the local MLX model backend); runs fully offline once a model is cached. Run: `PYTHONPATH=src .venv/bin/python scripts/interactive_app.py` then open `http://127.0.0.1:8000`. Backend + core logic live in the unit-tested `sts_ai.interactive` package (see [`src/sts_ai/interactive/CLAUDE.md`](../src/sts_ai/interactive/CLAUDE.md)); board HTML is the shared `sts_ai.rollout_view_html`.

## Area gotchas

- **A Hugging Face model ID is not a frozen base-model identity.** The local cache currently contains two materially different `mlx-community/gemma-4-e4b-it-bf16` revisions. COMP-015 training used revision `eec12d0899edea9b738ab1009af9159cdfd70d71`: the cache `main` ref already pointed there at 2026-07-23 02:40, before the retained COMP-015 checkpoints were created from 07:37 onward. Retained diagnostics must resolve and record the exact snapshot rather than loading the mutable repo ID. `score_direct_actions.py` therefore requires `--expected-model-revision`, loads that resolved local snapshot, and records its config/tokenizer/index and CAS weight identities.
- **`--max-tokens` must be large for reasoning/thinking models (default 4096).** A small cap (e.g. 256) truncates the model mid-thought, so it never emits the closing JSON: `parse_json_action` fails, the decision is marked invalid, and after retries the rollout stops with `agent_invalid` before executing any fallback action. The eval's `invalid_rate` + `completion_tokens` (pinned at the cap) make this obvious. Raising the cap is **free for no-thinking models** (generation stops at EOS ~60-90 tokens, well under the cap), so the high default costs nothing there.
- **An unrecoverable invalid decision now *ends the rollout* (`stopped_reason=agent_invalid`), so outcome metrics are only interpretable beside the invalid rate.** Floor/win-rate from `summarize_rollouts.py` / `compare_models.py` partly reflect format-compliance, not just policy quality: an arm that truncates JSON more often will score lower for format reasons. Always read the `unexecuted` / `stopped_reason` columns (and `audit_rollouts.py`) next to outcome — never compare arms (esp. thinking vs no-thinking) on outcome alone. See `docs/rl_and_framing_design.md` gotcha 1.
- **`run_rollout.py` deletes the output file if it already exists** before writing. Pass a fresh `--output` path if you need to keep a prior trace.
- Records are appended per-decision during the run; a crash mid-rollout leaves a partial JSONL file.
- **Release each diagnostic checkpoint before loading the next one.** `MlxCandidateScorer._load()` returns `(model, tokenizer)`; binding that model to a loop-scope throwaway such as `_` keeps it alive even after the scorer fields are cleared, so the next checkpoint can momentarily require two full models and OOM. Use the tokenizer-only helper, clear the scorer in `finally`, and keep final JSON reports on the atomic same-directory-temp-plus-`os.replace` path.
- **Streamlit HTML rendering in `visualize_rollout.py` has two sharp edges.** (1) Markdown treats any line indented ≥4 spaces as a code block, so each HTML tile/panel must be emitted as a **single-line** string (no pretty-printed newlines) via `st.markdown(..., unsafe_allow_html=True)`. (2) A rerun (e.g. autoplay/`st.rerun`) re-renders the page from scratch, so the `<style>` block is **re-emitted every run** rather than once — don't guard it behind a session flag or the tiles lose their CSS.
